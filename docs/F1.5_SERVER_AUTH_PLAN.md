### 2.1 Passwords are stored and compared in plaintext

```9:9:src/data/appDatabase.ts

```

That field is serialized whole into `localStorage['flyer_db_v1']` by `writeDb`

### 2.2 The session is a client-writable object

```24:33:src/contexts/AuthContext.tsx
  const [auth, setAuth] = useState<AuthState>(() => {
    const saved = localStorage.getItem("flyerrr_auth");
    return saved ? JSON.parse(saved) : { isLoggedIn: false, role: "student", userName: "" };
  });

  const login = (role: UserRole, name: string, options?: { email?: string; userId?: string }) => {
    const state = { isLoggedIn: true, role, userName: name, email: options?.email, userId: options?.userId };

    localStorage.setItem("flyerrr_auth", JSON.stringify(state));

```

The only gate in front of every privileged screen reads that object:

```28:30:src/App.tsx

  const { auth } = useAuth();
  if (!auth.isLoggedIn) return <Navigate to="/login" replace />;
```

One console paste grants the verification queue, attendance reports, and event creation:

```js
localStorage.setItem('flyerrr_auth', '{"isLoggedIn":true,"role":"org_officer"}')
```

### 2.3 A third hole the issue does not yet mention — add it

`role` is chosen by the user in the sign-up UI and passed straight into account creation.
The officer/student choice is two buttons on the login screen
(`src/pages/Login.tsx:66` and `:80`), and the selected value flows unvalidated into
`createUser`:

```26:33:src/pages/Login.tsx
    if (authMode === "signup") {
      if (!name.trim()) return;
      const result = createUser({ email, password, name, role });
```

Anyone can self-register as `org_officer`. That is a **privilege-escalation-by-signup**
defect, and it is arguably worse than the localStorage edit because it requires no
DevTools at all. Add it to issue #16 as a fourth piece of evidence and add a matching
acceptance criterion (see §6).

### 2.4 There is no server to move anything to

`package.json` has zero server, database, hashing, or session dependencies — no Express/
Fastify/Hono, no `pg`, no `bcrypt`/`argon2`, no `jose`. The repository contains one Vite
SPA. **F1.5 cannot be completed inside `src/`.**

## 4. Decisions to make and write down

Do not start Phase 2 until these are settled. Put them in
`docs/adr/0002-authentication.md` — the ADR directory is already required by F1.1.

| Decision | Recommendation | Why |
|---|---|---|
| Hash algorithm | **argon2id** if the host supports native modules; otherwise **bcrypt** at cost 12 | Both satisfy the criterion. Bcrypt is the safer choice for a student project on constrained hosting because it is pure-JS-friendly. |
| Session mechanism | **Opaque session ID in an httpOnly cookie**, row in a `sessions` table | The issue accepts "httpOnly cookies or short-lived JWTs," but the criterion also demands *revocation*. Revoking a JWT requires a denylist, which is a session table with extra steps. Skip the detour. |
| Cookie attributes | `httpOnly; Secure; SameSite=Lax; Path=/`, 7-day absolute expiry | `SameSite=Lax` works with the SPA on the same site. If staging ends up on a different origin than the client, you need `SameSite=None; Secure` **and** CORS `credentials: true` — settle this with Ogechi in §3 step 2. |
| Who can become an officer | Self-signup creates `student` **only**. Officer role is granted by an admin, or by the F17/F18 organization-verification flow. | Closes §2.3. Also lines up with US-08, which says an administrator approves org leaders before they can post. |
| Seed accounts | **Delete** `password123`. Provide a `server/scripts/seed-dev-users.ts` that reads passwords from env vars and refuses to run when `NODE_ENV=production`. | Satisfies "existing seed accounts migrated or reset" without breaking local demos. |
| Migration of existing plaintext users | Nobody real has an account. **Drop them.** Document that choice. | Writing a rehash-on-next-login migration for two fake accounts is wasted points. Say so in the ADR — "considered and rejected, with reason" scores better than silence. |

## 5. Work plan

Five phases. Phase 0 and 1 are unblocked today.

### Phase 0 — Groundwork (no dependencies) · ~0.5 pt

- [ ] Re-verify the evidence in §2 against the current `main` and update issue #16,
      including the `:179` → `:187` correction and the new §2.3 self-signup evidence.
- [ ] Write `docs/adr/0002-authentication.md` with the §4 decisions.
- [ ] Post the four coordination agreements from §3 as comments on issue #16.
- [ ] Open a draft PR early with the ADR only, so review starts before the code exists.

### Phase 1 — The contract (no dependencies) · ~1 pt

Write the API contract and the zod schemas first. This is the piece that lets you work
in parallel with F1.3 instead of behind it, and `zod` is already a dependency.

- [ ] `docs/api/auth.md` — endpoint table, request/response bodies, status codes,
      error codes, cookie behavior:

  | Method | Path | Purpose | Success | Failure |
  |---|---|---|---|---|
  | `POST` | `/api/auth/signup` | Create a **student** account | `201` + `Set-Cookie` + safe user | `409` email taken, `400` validation |
  | `POST` | `/api/auth/login` | Exchange credentials for a session | `200` + `Set-Cookie` + safe user | `401` generic, `429` throttled |
  | `POST` | `/api/auth/logout` | Revoke the current session | `204` + cookie cleared | `204` (idempotent) |
  | `GET` | `/api/auth/me` | Who am I, per the server | `200` safe user | `401` |

- [ ] Define the **safe user** DTO explicitly — `{ id, email, name, role, createdAt }`.
      No `password`, no `password_hash`, ever. Give it a name and a single serializer
      function so it cannot drift.
- [ ] `shared/schemas/auth.ts` — zod schemas for signup and login, exported for both the
      server (validation) and the client (form resolvers). Includes the university-email
      rule and a minimum password length.

### Phase 2 — Server implementation · ~2 pts · needs F1.3's process + F1.2's schema

- [ ] Migration adding `password_hash`, `role`, the case-insensitive unique email index,
      and the `sessions` table. Coordinate with F1.2 rather than writing a competing one.
- [ ] `server/src/lib/password.ts` — `hash(plain)` and `verify(plain, hash)`. Two
      functions, one file. This is the only place in the codebase that touches a plaintext
      password.
- [ ] `server/src/lib/session.ts` — create, look up, revoke, and sweep expired sessions.
- [ ] `server/src/routes/auth.ts` — the four endpoints. Login **always** does a hash
      comparison even when the email is unknown (compare against a dummy hash) so response
      timing does not reveal account existence.
- [ ] `server/src/middleware/requireAuth.ts` and `requireRole(...roles)`. These attach the
      session claim and are what F19 builds on — hand them to Ogechi.
- [ ] In-memory rate limiter keyed on `email + IP`, roughly 5 attempts per 15 minutes,
      with a documented lockout. Note in the ADR that a single-process limiter is
      sufficient at this scale and what would replace it (Redis) if it were not.
- [ ] Audit log writes on signup, login success, login failure, logout, and role change —
      actor, action, timestamp, IP. Never the password or the hash.

### Phase 3 — Client cutover · ~1 pt · needs F1.4's `UserRepository`

- [ ] `AuthContext` stops being the source of truth. Replace the `localStorage` read at
      `src/contexts/AuthContext.tsx:25` with a `GET /api/auth/me` query, and delete the
      write at `:32`. The `flyerrr_auth` key goes away entirely.
- [ ] `src/pages/Login.tsx` stops importing `authenticateUser` and `createUser` from
      `src/data/appDatabase` (line 9) and calls the repository instead. Remove the role
      argument from the signup path.
- [ ] Keep the role selector on the login screen as a *sign-in convenience* if the team
      wants it, but it must not be sent on signup. Or remove it — simpler, and the server
      knows the role anyway.
- [ ] Delete the `password` field from `AppUser` and the two `password123` seeds in
      `src/data/appDatabase.ts`. Any localStorage adapter that survives as the offline
      path stores the safe user DTO only.
- [ ] `ProtectedRoutes` in `src/App.tsx` renders a loading state while `/me` resolves, then
      redirects on `401`. State clearly in the PR description that this guard is now
      **UX only** and the real boundary is server-side.

### Phase 4 — Proof · ~0.5 pt

The acceptance criteria say "verified by test." These are the tests that do it.

- [ ] `password.test.ts` — the same password hashes to different values twice; `verify`
      accepts the correct password and rejects a wrong one.
- [ ] `signup.test.ts` — duplicate email returns `409`; a response body never contains
      `password` or `password_hash`; **a signup request that includes
      `role: "org_officer"` produces a `student` account.** ← closes §2.3.
- [ ] `login.test.ts` — wrong password and unknown email return the *byte-identical*
      generic message; the 6th attempt in the window returns `429`.
- [ ] **The bypass test.** Set `flyerrr_auth` to `{"isLoggedIn":true,"role":"org_officer"}`
      with no valid cookie, then call the officer-only endpoint. Assert `401`/`403` and
      assert the database is unchanged. This single test is what the Definition of Done in
      `docs/BACKLOG_INTEGRATION.md` Issue 2 asks for — name it so a grader can find it.
- [ ] `logout.test.ts` — the session row is gone and the cookie no longer authenticates.
- [ ] `grep -rn "password" src/` shows no plaintext storage or comparison.
- [ ] `npx tsc --noEmit -p tsconfig.app.json`, `npm run lint`, `npm test`, and
      `npm run build` all pass. Add the auth tests to `.github/workflows/ci.yml` (F3.1).

## 6. Acceptance criteria — copy back into issue #16

The first six are the current criteria. Three are new, and you should add them.

- [ ] Passwords hashed with bcrypt or argon2, server-side only
- [ ] No credential is ever written to client storage
- [ ] Session tokens are httpOnly cookies or short-lived JWTs
- [ ] Every privileged endpoint enforces role server-side
- [ ] Editing localStorage cannot grant officer access — verified by test
- [ ] Existing seed accounts migrated or reset
- [ ] **New —** A signup request cannot set its own role; self-registration always yields
      `student`, verified by test
- [ ] **New —** Login failures return an identical generic message for unknown-email and
      wrong-password, and are rate-limited
- [ ] **New —** `docs/adr/0002-authentication.md` records the hash algorithm, session
      mechanism, and cookie policy with at least two alternatives considered

## 7. Definition of done

A teammate on a clean checkout can sign up, sign in, and reach the feed; the `users` table
shows an argon2/bcrypt hash and no plaintext anywhere; and an automated test proves a user
who tampers with client state cannot reach any officer-only screen or endpoint.
